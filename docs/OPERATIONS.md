# 동국 규정 MCP — 공동 이용 운영 가이드

대상 버전: v0.12.0. 기본 배포는 공개 규정 조회용 `rules` 프로필입니다. 이 문서는 운영자가 반복할 절차이며, 기관 승인·담당자 배정·전교 사용자 실증·가용성 SLA의 완료 증빙은 아닙니다.

## 1. 프로필과 접속 경계

| 구성 | 목적 | 운영 기준 |
|---|---|---|
| `rules` — 기본값 | 공개 교내 규정 조회 | 내부 재무지식팩과 로그인 쿠키를 사용하지 않는 일반 구성원 배포 |
| `finance` — 선택 | 공개 규정·한국법령 공동 조회 및 별도 구성한 내부 자료팩 | `--profile finance` 또는 `DONGGUK_MCP_PROFILE=finance`, 승인된 이용 범위 내 운영 |
| `POST /mcp/rules` | 공개 규정 도구 전용 공용 경로 | 서버가 `finance`여도 규정 전용 경로이며 인증 유지 |
| `POST /mcp` | 해당 서버 프로필의 MCP 경로 | 기존 연결 호환, 운영자가 설정한 프로필과 접근권한 확인 |

일반 구성원에게는 로컬 `rules` 설치 또는 인증된 `/mcp/rules` 경로를 안내합니다. `finance` 프로필 활성화, 내부 지식팩 배포, 로그인 쿠키 사용은 각각 독립적으로 관리합니다. 기존 Finance AI Desk 연결이 있다면 프로필 변경 전 도구와 권한의 영향을 확인합니다.

규정 전용 경로가 있다는 이유로 인터넷 무인증 공개가 허용되는 것은 아닙니다. HTTPS와 사용자 또는 그룹별 접근통제를 구성하고, 관리자 인증정보 하나를 전 구성원에게 나누어 주지 않습니다. 기관 SSO·이용자 명부 연계·자동 계정 회수는 별도 인프라와 운영 절차가 필요한 항목입니다.

## 2. 역할 지정

| 역할 | 책임 | 남길 기록 |
|---|---|---|
| 서비스 운영자 | 버전·배포·인증·장애·복구 | 배포/복구 시각, 버전, 진단 결과 |
| 규정·업무 검토자 | 적용범위·시점·표·해석 오류 검토 | 근거 위치, 판정, 미해결 사항 |
| CoP 진행자 | 실습·질문 수집·타 부서 재사용 | 비식별 질문, 교육 및 연결 성공 기록 |
| 평가 담당자 | 전후 비교와 실패 포함 측정 | 원점수, 시간, 오류, 조건 |

실명·연락처·인증정보는 공개 저장소가 아닌 기관의 운영 기록에 보관합니다. 담당자가 지정되지 않았으면 “운영책임자 미지정”으로 남기고, 이 문서가 자동으로 업무를 배정한 것으로 처리하지 않습니다.

## 3. 배포 전 확인

복구할 기존 패키지 버전과 설정의 위치를 기록하고, 비밀값이 포함된 설정은 접근제한 영역에 백업합니다. 소스 변경이 없는 배포라면 이미 통과한 같은 버전의 전체 테스트를 불필요하게 반복하지 않아도 되지만, 배포 대상 환경의 기동·인증·원문 조회는 확인합니다.

소스에서 릴리스를 검증할 때:

```bash
npm ci
npm test
npm run test:live
npm pack --dry-run
node src/index.js --version
node src/index.js --doctor --json
```

다음 내용을 배포 기록에 남깁니다.

- 태그·커밋·패키지 파일명·해시와 Node 버전.
- 오프라인 회귀 결과, 실원문 조회 결과, 미실행 또는 실패한 검사.
- `rules`에서 재무 도구가 노출되지 않는지와 `finance`의 선택 연결 상태.
- 공용 경로의 인증 없는 요청 거절, 올바른 인증의 호출 성공, 폐기된 인증의 거절.
- 공개 패키지·로그·문서에 내부 지식팩, 쿠키, 인증값, 개인별 자료가 포함되지 않는지.

태그 고정 설치 예시:

```bash
npx -y https://github.com/buenosiempre-cmd/dongguk-rule-mcp/releases/download/v0.12.0/dongguk-rule-mcp-0.12.0.tgz --version
```

`latest`나 개발 브랜치가 자동으로 운영에 반영되도록 구성하기보다 검증한 릴리스 단위를 설치합니다. 기존 프로세스는 패키지 파일을 교체해도 구버전을 계속 사용할 수 있으므로 재시작 후 버전을 다시 확인합니다.

### 클라이언트와 기존 연결 갱신

파일 설치, 실행 중인 서버, 앱이 이미 연결한 MCP 프로세스는 서로 다른 상태입니다. 다음 세 버전을 별도로 기록합니다.

| 확인 지점 | 확인 방법 | 의미 |
|---|---|---|
| 설치 런타임 | 실제 런처가 가리키는 실행 파일의 `--version` | 다음 시작에 사용할 코드 |
| 공용 HTTP 서버 | `/health`, 이어서 인증된 `get_service_info` | 현재 요청을 받는 서버 |
| Codex·Aside 실제 연결 | 각 앱에서 `get_service_info` 호출 | 해당 앱의 현재 연결이 쓰는 코드 |

1. 새 버전은 별도 디렉터리에 설치하고 검증한 뒤 기존 런처의 대상 경로를 바꿉니다. 공개용과 내부용 런처, 쿠키·인증 헤더·자료팩·한국법령 연결은 기존 경계를 보존합니다.
2. Mac mini의 해당 MCP HTTP 서비스만 재시작합니다. 터널이나 다른 앱을 함께 재시작할 필요는 없습니다. 인증 거절·허용 경로·대표 원문 비교를 다시 확인합니다.
3. Codex의 기존 stdio 연결은 패키지 교체 후에도 구버전을 유지할 수 있습니다. 기존 연결을 확실히 갱신하려면 진행 중인 작업을 정리하고 Codex 앱을 완전히 종료한 뒤 다시 실행합니다. 앱 재시작은 실행 중인 대화를 중단할 수 있으므로 배포·검증을 끝낸 후 시행합니다. 재실행 후 실제 `get_service_info` 응답을 받기 전에는 “기존 연결 갱신 완료”로 기록하지 않습니다.
4. Aside는 실행 중인 데몬이 설정 파일을 덮어쓸 수 있으므로 `settings.json`을 직접 고치지 않습니다. `aside skills show aside`로 현재 공식 API를 확인하고, `aside repl --account u0`에서 `aside.settings.get('mcp')`로 읽은 설정을 보존한 채 `aside.settings.set('mcp', ...)`를 사용합니다. 새 런타임의 `tools/list`로 확인한 해당 서버의 `inventories`만 갱신하고 `refreshedAt`은 `Z`로 끝나는 UTC 시각으로 저장합니다. 기존 `servers`와 다른 도구 목록을 바꾸지 않았는지 재조회해 확인합니다. 실제 계정 ID는 운영 환경에 맞춥니다.
5. Aside 도구 목록 저장 성공은 도구 실행 성공과 다릅니다. Aside에서 `get_service_info`와 대표 비교를 호출해 버전·결과를 확인합니다. 연결이 구버전을 유지하면 해당 앱의 재연결 절차를 진행하고 다시 확인합니다.

### HWP 구조 비교와 캐시 전환

v0.12.0은 원문 캐시 이름을 `original-structure-v1`로 분리합니다. 이전 텍스트 전용 원문 캐시를 구조 분석 결과로 재사용하지 않으며, 첫 조회에서 HWP를 다시 받아 셀·병합 범위·그림 파일과 문서별 추출 진단을 저장합니다. 전체 캐시나 사용자 설정을 지울 필요는 없습니다. 이전 버전으로 롤백해도 새 구조 캐시를 이전 형식으로 읽지 않습니다.

대표 검증에는 HWP 조문 변경, 표의 값·행/열 병합 변경, 그림 파일 내용 변경, HWP 실패 시 HTML 부분 비교, 미지원 객체·추출 누락의 진단을 포함합니다. 그림 비교는 포함된 파일 바이트의 SHA-256 비교이며 OCR·의미 해석·페이지 배치 검증을 포함하지 않습니다. 결과와 실제 미지원 항목을 함께 보고하고, 한 문서의 성공을 모든 HWP 형식에 대한 보장으로 확대하지 않습니다.

## 4. 공용 서버 기동과 검수

원격 인증은 접근제한 서비스 환경파일 또는 비밀 관리 기능에서 주입합니다. 토큰을 명령행 인자·문서·쉘 기록에 직접 적지 않습니다. 공용 운영은 다중 자격증명 파일로 개인/그룹과 운영자 권한을 관리합니다. 기존 관리자 자격증명을 전 구성원 배포에 재사용하지 않습니다.

다중 자격증명 파일은 `--token-file /운영용/절대경로/tokens.json` 또는 `DONGGUK_MCP_TOKEN_FILE`로 지정합니다. JSON 최상위 `tokens` 배열의 각 항목에는 다음 속성을 둡니다.

| 속성 | 의미 |
|---|---|
| `id` | 개인 이름 대신 사용하는 관리용 ID |
| `sha256` | 발급 토큰의 SHA-256 해시, 64자리 16진수; 평문 토큰은 저장하지 않음 |
| `enabled` | `true` 사용, `false` 회수 |
| `expiresAt` | UTC 만료시각 |
| `endpoints` | 허용 경로 배열, 일반 이용자는 `["/mcp/rules"]`; 생략해도 규정 전용 경로만 허용 |
| `admin` | `true`인 관리용 자격증명만 `/status` 조회 가능; 일반 이용자에게 지정하지 않음 |

승인된 이용자 또는 그룹에 대한 발급 예시입니다. 경로는 실제 접근제한 운영 폴더로 바꾸고, 출력 토큰 파일은 해당 이용자에게 별도 보안 경로로 전달합니다.

```bash
npm run issue-token -- --id member-001 --registry /secure/dongguk/tokens.json --out /secure/dongguk/member-001.token --expires 2027-01-01T00:00:00Z
```

이 명령은 토큰을 보안 파일로, 해시는 등록 파일로 저장하기 위한 운영자 도구입니다. 파일 생성과 실제 이용자 발급·전달은 별도 기록합니다. 이 배포 가이드가 이용자 명부를 수집하거나 계정을 자동 개통하지는 않습니다.

토큰 파일은 서버 시작 시 읽습니다. 등록·변경·회수한 뒤에는 서버를 재시작하고 새 자격증명의 성공과 회수된 자격증명의 거절을 확인합니다. 등록 파일은 **최대 16,384항목·4MiB**를 지원하고 SHA-256 해시를 Map으로 조회합니다. 항목 수와 파일 크기 제한을 모두 만족해야 합니다. 운영자가 이용자별 또는 그룹별 발급을 선택할 수 있으며, 발급 대상·만료·회수 책임을 별도로 관리합니다. 기관 SSO·명부·자동 계정 회수와는 연결되어 있지 않습니다. 해시 파일도 접근제한을 유지하고 Windows에서는 서비스 계정의 파일 접근권한을 함께 설정합니다.

### 기존 관리자 연결을 등록 파일로 이전

`--token` 또는 `DONGGUK_MCP_TOKEN`을 함께 설정하면 기존 단일 토큰은 만료 없는 관리자 자격증명으로 추가됩니다. 같은 토큰의 해시가 등록 파일에도 있을 때는 이 기존 설정이 우선하므로, 등록 파일에서 `enabled:false`로 바꾸거나 만료시켜도 기존 설정이 남아 있으면 회수되지 않습니다.

운영자도 등록 파일의 활성화·만료·허용 경로로 관리하려면 다음 순서로 이전합니다.

1. 접근제한 환경에서 기존 토큰의 SHA-256 해시를 `operator` 같은 관리용 ID로 등록합니다. `admin:true`와 필요한 MCP 경로를 지정하고, 평문 토큰을 기록·출력하지 않습니다.
2. 서버 실행 설정에서 평문 `DONGGUK_MCP_TOKEN`의 export와 `--token` 인자를 제거합니다. 상위 환경에서 상속되지 않도록 실행 전에 `unset DONGGUK_MCP_TOKEN`도 적용합니다.
3. `--token-file` 또는 `DONGGUK_MCP_TOKEN_FILE`만 사용하는 상태로 재시작합니다. 기존 사용자에게 저장된 토큰 값은 바뀌지 않으며, 같은 해시의 등록 항목이 활성·허용된 동안 연결이 유지됩니다.
4. 별도 시험 자격증명의 비활성화·만료·경로 거절을 확인하고 운영자의 발급·회수 책임을 기록합니다.

CoP 초기 접속용 그룹 자격증명은 `/mcp/rules`만 허용하고 만료를 설정해 별도로 발급할 수 있습니다. 평문은 접근제한 로컬 파일로 저장해 정해진 이용 범위에 전달하고, 관리자 권한은 부여하지 않습니다. 그룹 자격증명 발급을 모든 구성원의 개별 계정 개통 또는 기관 SSO 연결로 보고하지 않습니다.

```bash
# 접근제한 서비스 설정에서 인증을 주입한 상태에서 실행
unset DONGGUK_MCP_TOKEN
node src/index.js --http --profile rules --host 127.0.0.1 --port 3845 --token-file /secure/dongguk/tokens.json
```

외부 공개는 HTTPS 프록시 또는 운영 중인 터널을 통해 `/mcp/rules`로 연결합니다. 프록시는 요청 크기·연결 제한과 인증 헤더 전달을 실제 환경에서 점검합니다. 직접 인터넷에 평문 HTTP를 노출하지 않습니다.

배포 후에는 다음 순서로 상태를 구분해 확인합니다.

1. `GET /health`로 프로세스와 배포 버전 확인.
2. 인증된 MCP 연결에서 `get_service_info`와 `tools/list` 확인.
3. `lookup_dongguk_rule`의 공개 규정 검색·원문·개정본 식별자 확인.
4. 구성원이 사용하는 실제 앱에서 같은 질문을 실행.
5. 다른 캠퍼스·직군의 대표 사용자가 적용범위 근거를 확인할 수 있는지 실증.

`/health`의 성공은 원문 서버, HWP 추출, 인증, 실제 앱 연결까지 정상이라는 뜻이 아닙니다. `GET /ready`는 프로세스의 요청 수용 상태만 확인하며, 관리용 인증이 필요한 `GET /status`는 집계 운영 상태를 확인하는 경로입니다. 서로 다른 검증 상태를 하나의 “전체 정상”으로 합치지 않습니다. 공개 endpoint에서 인증된 호출을 검증하지 못했다면 그 항목을 미검증으로 기록합니다.

## 5. 인증과 데이터 관리

- 구성원에게는 필요한 경로와 도구만 허용하고, 발급 대상·만료/회수일·담당자를 별도 기록합니다.
- 자격증명이 유출되면 즉시 폐기·재발급하고 영향 범위와 접속 기록을 확인합니다. 비밀값 자체를 사고 기록에 복사하지 않습니다.
- 로그에는 시각·버전·도구·지연·상태·오류코드를 우선 기록합니다. 질문 원문·인용 검증에 넣은 문서·응답 본문·쿠키·토큰을 기본 수집 대상으로 삼지 않습니다.
- 공개 `rules` 캐시와 인증된 원문/재무 서비스를 분리합니다. 로그인 쿠키가 필요한 사용은 선택한 `finance` 프로필과 승인된 범위에서만 운영합니다.
- 익명화되지 않은 내부 매뉴얼·급여·학생·신고자료를 공개 배포에 포함하지 않습니다. 검토된 재무지식팩도 공개 코드와 별도로 배포합니다.

## 6. 정기 확인과 용량 계획

### Mac mini에서 운영하는 공용 서버

공용 서버를 Mac mini에서 운영할 때는 서비스 프로세스뿐 아니라 전원·잠자기·로그인 이후 자동 실행·인터넷·HTTPS 터널의 상태를 함께 확인합니다. OS 업데이트나 재부팅 뒤에는 프로세스와 터널이 다시 시작하는지, 인증과 공개 원문 조회가 복구되는지 확인합니다. 로컬 컴퓨터의 잠자기 방지나 자동 실행 설정은 해당 장비의 운영 정책에 맞춰 별도로 관리합니다.

Mac mini가 꺼지거나 잠자기에 들어가거나 인터넷이 끊기면 공용 MCP와 안내 페이지도 중단될 수 있습니다. 이런 환경에서 24시간 가용성 또는 SLA를 약속하지 않습니다. 장애 시 이용자는 공식 규정 시스템이나 개인 PC의 `rules` 설치 경로를 사용할 수 있지만 공식 원문 서버 자체가 장애인 경우 개인 설치로 해결되지는 않습니다.

공용 안내 페이지는 `/`와 `/guide`에서 제공하며 외부 스크립트·폰트·외부 자원을 불러오지 않는 `docs/quickstart.html`을 사용합니다. 내용은 개인/그룹 자격증명 발급이 필요한 공용 연결과 공유 토큰이 필요 없는 개인 설치를 구분합니다. 안내 페이지 공개 자체가 기관 승인·전원 통지·계정 개통을 뜻하지 않습니다.

초기 CoP에서는 주 1회 운영자가 버전·대표 조회·원문 개정 이력·실패 기록을 확인하는 계획을 권합니다. 이 가이드 자체는 정기 자동화나 알림을 생성하지 않습니다.

여러 부서로 넓히기 전에는 대표 동시 사용자 수를 정하고 정상 요청·인증 실패·느린 원문·요청 제한 상황을 확인합니다. 서버 자원, 지연의 중앙값/상위 구간, 오류율, 원문 서버에 보내는 요청 수를 측정해 허용량을 정합니다. 코드의 동시 요청 제한과 캐시는 전교 규모 부하 검증 또는 SLA를 대신하지 않습니다.

규정 개정 발견 시에는 과거 근거 기록을 지우지 않고 새 HISTORY_ID와 조회일을 추가합니다. 이를 인용한 FAQ·교육 예시·질문카드를 재검토 대상으로 표시합니다. 개정본 ID 변경만으로 특정 금액·권한이 달라졌다고 공지하지 않습니다.

## 7. 장애 대응

| 증상 | 확인 순서 | 이용자에게 안내할 상태 |
|---|---|---|
| 도구 연결 실패 | 앱 설정/재시작 → 실행 경로 → 서버/프록시 | 연결 실패, 규정 내용은 확인하지 못함 |
| `401` 인증 실패 | 자격증명 발급·회수 → Bearer 전달 → 허용 경로 | 접근권한 확인 필요 |
| 요청 제한/과부하 | 동시 요청·요청량 → 재시도 간격 → 원문 지연 | 잠시 후 재시도, 결과 미확인 |
| 원문 HTTP 오류 | 공식 사이트 상태 → 운영 네트워크 → 재시도 | 원문 조회 실패, 오래된 답변을 최신으로 단정하지 않음 |
| HWP 실패·HTML 대체·빈 발췌 | 원문 파일 직접 확인 → 추출 경고·표 존재 확인 | 부분 조회, 표 근거 재확인 필요 |
| 잘못된 캠퍼스·직군·시행일 적용 | 해당 답변·근거 기록 → 업무 검토 → 재현 | 해당 흐름 수정 전 확산 중지 |
| 내부자료/자격증명 노출 | 노출 경로 중지·자격증명 회수 → 영향 확인 | 기관 사고대응 절차에 따라 안내 |

원문 장애를 근거 없이 “해외 IP 차단” 또는 “규정 없음”으로 확정하지 않습니다. 장애 중에는 [공식 규정 시스템](https://rule.dongguk.edu/)에서 사람이 원문을 확인하는 경로를 함께 안내합니다.

## 8. 롤백과 완료 판정

장애가 새 릴리스에서 재현되면 검증해 둔 직전 패키지와 설정으로 복구하고 프로세스를 재시작합니다. 복구 후 버전·프로필·인증·대표 원문 조회를 다시 확인합니다. 새 설정이 이전 버전과 호환되지 않을 수 있으므로 패키지뿐 아니라 해당 버전의 설정 백업도 사용합니다.

배포 보고에는 아래를 따로 씁니다.

- **완료:** 공개 릴리스·패키지·문서·검증 등 실제 증거가 있는 작업.
- **부분:** 로컬 또는 일부 경로에서만 확인한 연결·동작.
- **미검증:** 실제 구성원 앱, 캠퍼스/직군별 적용 실증, 동시 이용 규모, 업무시간 개선 등 아직 측정하지 않은 항목.
- **보류:** 기관 계정·승인·담당자 지정 등 외부 조건이 필요한 작업과 그 사유.

기관 SSO와 전 구성원 명부가 연결되어 있지 않으면 “전원 설치 완료”라고 보고하지 않습니다. [구성원 가이드](COP_GUIDE.md)와 [실증평가 양식](EVALUATION.md)을 배포하더라도 실제 통지·교육·계정 개통·효과 측정은 각 증빙으로 확인합니다.
