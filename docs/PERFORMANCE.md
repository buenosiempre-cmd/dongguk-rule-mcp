# 빠른 규정 조회

## 구성원 사용법

처음 연결할 때만 `get_service_info`로 버전·범위를 확인합니다. 평소에는 규정명과 핵심어를 넣어 `lookup_dongguk_rule`을 바로 호출합니다. `search_rule` → `list_rule_history` → `get_rule_content`를 따로 호출하는 흐름을 줄일 수 있습니다.

예시 질문:

> 여비규정의 국내 숙박비 기준을 찾아줘. 관련 조문·별표와 공식 원문 링크를 먼저 보여주고 핵심만 짧게 정리해줘. 근거가 부족하거나 잘렸으면 그 부분만 추가 확인해줘.

앱 또는 에이전트 지침에 넣을 수 있는 문장:

> 동국대학교 현행 규정 질문은 lookup_dongguk_rule부터 호출한다. 연결 진단을 요청받았을 때만 get_service_info를 호출한다. 한 번의 결과에 필요한 조문·별표와 원문 링크가 있으면 동일한 검색·본문·목차를 중복 조회하지 않는다. partial, 발췌 잘림, 후보가 여러 개인 경우에는 필요한 부분만 추가 조회한다. 과거 기준일은 applicable_rule로 별도 확인하고 시행일·적용범위를 확인한다. 답변은 핵심과 근거부터 짧게 제시한다.

서버 조회시간과 AI가 생각하고 답을 작성하는 시간은 별개입니다. 답변을 짧게 요청하거나 통합 도구로 호출 횟수를 줄이면 앱에서 대기하는 시간을 줄일 여지가 있지만, 모든 앱의 총 응답시간을 보장하지는 않습니다.

## 공용 서버의 공개 규정 사전 준비 (v0.10.3)

HTTP 서버를 시작할 때 아래 환경변수를 설정합니다. 기본값은 빈 목록이며, stdio 모드에는 주기 작업을 만들지 않습니다.

```sh
export DONGGUK_MCP_WARM_RULES='여비규정,위임전결규정,재정시행세칙(학생자치기구)'
dongguk-rule-mcp --http --profile finance
```

기존 운영의 host·port·token-file 등은 그대로 사용합니다. 이 예시는 기존 인증 설정을 대체하는 명령이 아닙니다. 규정명은 최대 8개이며 조회량을 확인하면서 필요한 대상만 등록합니다.

- 서버가 요청을 받을 준비를 마친 뒤 별도로 시작합니다. 초기 사전 준비가 끝나기 전의 첫 요청은 여전히 원문 조회를 기다릴 수 있습니다.
- 한 규정씩 실행하고, 사용자 요청이 실행·대기 중이면 다음 규정은 미룹니다. 이미 실행 중인 사전 조회 1건은 끝까지 진행될 수 있습니다.
- 한 회차가 끝난 뒤 60초 후에 다시 확인합니다. 캐시가 신선하면 원문 서버에 요청하지 않습니다.
- 설정한 공개 규정의 검색·연혁·원문 캐시가 수명의 80%에 도달하면 만료 전에 갱신합니다. 연혁은 10분 만료를 유지하며, 계속 유휴 상태라면 약 8~9분에 다시 확인합니다.
- 갱신 중에도 만료 전 캐시는 즉시 사용할 수 있습니다. 만료됐으면 새 조회 성공을 기다립니다. 장애가 나도 만료된 규정을 최신처럼 돌려주지 않습니다.
- 백그라운드 갱신 실패는 유효 캐시가 남아 있는 동안 60초 재시도 간격을 둡니다. 사용자 요청에서 만료됐을 때의 조회는 이 대기시간에 묶이지 않습니다.
- finance 서버에서도 사전 조회는 항상 rules 프로필로 실행합니다. 학교 로그인 쿠키와 내부 재무자료는 사전 조회하지 않으며, 쿠키별 비공개 캐시는 분리됩니다.
- `DONGGUK_MCP_NO_CACHE=1`이면 사전 준비도 비활성화됩니다. 환경변수를 비우고 MCP 서버를 다시 시작하면 사전 준비 기능만 끌 수 있습니다.

운영자 인증이 필요한 `/status`의 `cacheWarmup`에서 enabled·ruleCount·cycles·completed·failed·deferred·running·lastFinishedAt을 확인합니다. 규정명·질문·토큰은 이 상태 응답에 포함하지 않습니다. completed는 준비 루틴 성공 횟수이며 완전한 업무 근거나 실제 사용자 수를 뜻하지 않습니다.

## 측정할 항목

동일 규정·인자로 캐시 없는 첫 조회, 사전 준비 완료 후 첫 사용자 조회, 반복 조회를 분리해서 비교합니다. 사전 준비에 든 시간과 원문 요청 수도 따로 기록해야 합니다. AI 답변 시간, 네트워크 경로, 다른 규정의 최초 조회, 서버가 계속 바쁜 상황은 별도 측정 대상입니다. 캐시 사전 준비는 원문 처리 비용을 사용자 요청 전으로 옮기는 기능입니다.

## 2026-10-07 실측

Node 22.22.3/macOS에서 v0.10.2와 v0.10.3 HTTP 서버를 번갈아 실행했습니다. 매 회차 별도 빈 캐시를 쓰고, 위 3개 정확한 규정명으로 동일 인자를 호출했습니다. 각 버전 3회차이며 p95는 nearest-rank 방식입니다.

| 조건 | 표본 수 | 중앙값 | p95 | 요청 중 원문 HTTP 호출 |
|---|---:|---:|---:|---:|
| v0.10.2 빈 캐시 첫 조회 | 9 | 1,671.6 ms | 2,048.9 ms | 33 |
| v0.10.3 사전 준비 후 첫 조회 | 9 | 5.8 ms | 26.7 ms | 0 |
| v0.10.2 반복 조회 | 45 | 2.3 ms | 6.6 ms | 0 |
| v0.10.3 반복 조회 | 45 | 2.0 ms | 3.4 ms | 0 |

로컬 HTTP 왕복 기준으로 AI 답변과 외부 터널 시간은 제외했습니다. 사전 준비 중앙값은 약 6.18초이며 매 회차 원문 요청 11회를 미리 수행했습니다. 전체 원문 요청 수는 양쪽 모두 회차당 11회로, 요청 자체가 사라진 것이 아닙니다. 108개 응답의 규정별 발췌 해시가 같았습니다. 작은 표본이며 총 앱 응답시간 또는 동시 이용자 수를 보장하지 않습니다.

최초 측정의 `재정시행세칙`은 정확한 제목이 아니어서 기존 버전이 `AMBIGUOUS_RULE`을 반환했습니다. 원문 확인 후 `재정시행세칙(학생자치기구)`로 고쳐 양쪽을 처음부터 다시 측정했습니다. 사전 준비 목록도 정확한 규정명으로 지정해야 합니다.
