# 번호 없는 HTML 본문과 캐시 이행

HTML 파서는 `article_none` 본문과 `hang_none` 계속 문장을 보존한다. `ho_none`, `mok_none`, `dann`, `dann_none`, `addendacontent_none`도 문서 순서대로 보존하고 실제 빈 조문·삭제 표시·부칙 경계를 유지한다.

## 캐시 계약: 옛 v3 명시적 무효화

- 현재 HTML 본문은 `content-v4`에서 읽고 새로 파싱한 결과도 그곳에 저장한다. 이미 새 파서로 만든 v4 캐시는 기존 TTL 규칙으로 바로 읽는다.
- `content-v3`는 읽거나 수정·삭제하지 않는다. 파싱 뒤 이미 잃은 문장을 복구할 수 없으므로 v3를 v4로 이름만 바꾸거나 복사하지 않는다. v4가 없거나 만료되면 공식 HTML을 다시 받아 새 파서로 처리한다. 원문 조회가 실패하면 실패로 남기며 v3로 조용히 폴백하지 않는다.
- 전문 색인에는 `contentVersion: 4`를 기록한다. 버전이 없거나 다른 색인은 검색에서 거부하고 기존 공식 사이트 조회 경로를 따른다. 인터넷 연결이 없으면 해당 조회가 실패할 수 있다.
- `--build-index`는 옛 파서 색인의 조문을 같은 연혁이라도 재사용하지 않는다. 이전 색인은 규정 수 급감 방지 비교용으로만 읽는다. 현재 버전·같은 연혁의 색인만 재사용한다.
- 기존 파일은 보존하며 실제 공유 캐시를 일괄 변경하는 명령을 실행하지 않는다.

v4가 없는 첫 조회는 원문을 요청한다. 조회 실패에는 기존 오류 분류가 적용된다. HTTP 429·5xx와 네트워크 장애는 `UPSTREAM_UNAVAILABLE`, 분류되지 않은 예외는 `INTERNAL_ERROR`로 반환될 수 있다. 캐시 부재만을 나타내는 오류 코드는 없다. 본문을 얻었지만 내용이 비어 있는 자연어 조회는 기존 `CONTENT_UNAVAILABLE` 경로를 따른다.

자연어 조회의 `original-structure-v2` HWP 우선 경로는 그대로다. 유효한 HWP 본문을 얻으면 HTML 대체 경로로 내려가지 않는다. 이번 누락은 HTML 클래스 처리에 한정되고 HWP 변환·구조 저장 형식은 바뀌지 않아 HWP 캐시 버전은 유지한다.

## 운영 이행

1. 코드 업데이트 후 서버와 같은 계정·`XDG_CACHE_HOME`에서 `dongguk-rule-mcp --build-index`를 실행한다.
2. HTTP 서버의 인증된 `/status`에서 `fullTextIndex.available`, 마지막 갱신 결과와 실패 규정 수를 확인한다. 저장된 `corpus/corpus-v1.json`의 `contentVersion`은 4여야 한다.
3. 이행 전후 corpus 해시와 실행 커밋을 기록한 뒤 공개 회귀를 확인한다. 이미 새 파서로 만든 content-v4·contentVersion4 corpus를 사용하면 재수집 없이 읽을 수 있다.

자동 전문 색인 갱신을 켠 HTTP 서버는 수신 시작 직후 비동기로 한 번 갱신한다. 첫 갱신이 실패해도 서버 기동은 유지되고 다음 주기에 재시도한다. 이 과정은 수동 배포 점검을 대신하지 않는다. stdio에는 자동 갱신이 없으므로 빌드 명령을 실행해야 한다. 구 색인이 거부된 후 새 색인이 준비되기 전에는 검색 성능·가용성이 떨어질 수 있다.

자동 갱신을 켜면 기동마다 갱신을 시도한다. 캐시가 없거나 만료된 목록·연혁·본문은 그때 원문 요청이 나간다. 유효한 캐시와 같은 연혁의 현재 파서 색인은 재사용하므로 매번 전체 본문을 받는 것은 아니다. 요청 시작 간격은 최소 0.5초다. 513개 본문을 모두 다시 받을 때 간격만으로 약 256초(4.3분)가 필요하며, 목록·연혁 요청과 응답·파싱 시간은 추가된다. 이는 계산상 최소 소요이며 전체 재수집 시간을 실측한 값은 아니다.

## 회귀 검증

`test/test-content-parser.js`는 번호 없는 조문과 계속 문장을 담은 합성 HTML로 본문 보존, 순서와 중복, 같은 연혁 재사용, 버전 불일치 거부, v3 보존, 실패 시 v3 폴백 금지를 검사한다. `test/test-index-startup.js`는 실제 HTTP 프로세스에서 기동 갱신 비차단·첫 실패 후 재시도·중복 빌드 방지·옛 색인 이행을 검증한다. 두 파일은 전체 `npm test`에 포함된다.
