# 유지보수 및 유사 MCP 개선 검토

기준일: 2026-11-05. 검토 시작 시 GitHub 소스는 v0.12.0(`2009703`)이었다. 현재 코드와 공개 저장소의 README·관련 구현, 공식 MCP SDK 문서를 대조했다. 외부 MCP의 기능 설명은 확인했으나 해당 서비스 전체의 동작 품질이나 업무 정확도를 검증한 것은 아니다.

이번 유지보수와 별도로 검토할 새 기능은 **일괄 개정 점검 → 규정 간 인용 조회 → 평가 자료를 갖춘 한국어 의미검색** 순서가 적합하다. 하위규정 정비 후보 점검은 인용 관계를 확보한 다음 확장한다. 기존 연혁·기준일 조회·인용 검증·구조화 오류·발췌 잘림 표시는 이미 구현되어 있어 기능을 중복 추가하지 않는다.

## 이번 반영 범위

v0.12.1 개발판에 아래 변경을 반영했다. 실제 확인 결과와 설치·공용 서버 상태는 문서 끝에 구분해 기록한다.

| 항목 | 반영 내용 | 목적 |
|---|---|---|

원문 캐시는 `original-structure-v2`로 전환했다. 이전 캐시의 조문 소속 누락이 새 비교를 가리지 않도록 새로 조회하며, 소속을 알 수 없는 구조는 `partial`로 남긴다. 도구 제목은 한국어 `title` 필드이며 표시 여부는 클라이언트에 달려 있다.

`@hono/node-server` 2.1.6은 `hono` 패키지의 버전을 뜻하지 않는다. 의존성은 `npm-shrinkwrap.json`으로 실제 설치 버전을 고정한다. 알려진 의존성 보안 권고는 moderate 1건에서 0건으로 줄었다. [공식 권고](https://github.com/advisories/GHSA-rmxm-3fg6-px4f)는 `serveStatic` 경로의 이중 디코딩 문제이며, 이 프로젝트에서 실제 공격 경로가 재현됐다는 뜻은 아니다. 새 기능 제안은 이번에 구현하거나 예약 실행을 등록했다는 의미가 아니다.

## 1. 일괄 규정 개정 점검

**우선순위 높음 / 구현 난도 중간.** 여비·보수·위임전결 등 여러 규정을 개별 조회하는 반복 작업을 줄인다. 우선 저장 상태가 없는 읽기 전용 도구로 시작하면 별도 데이터베이스 없이 기존 연혁·비교 기능을 활용할 수 있다.

제안 도구 계약:

```text
check_rule_updates(
  law_ids: integer[],                 # 1~20개, 중복 제거
  previous?: { [law_id]: history_id } # 이전 응답의 스냅샷
)

data: {
  checkedAt,
  results: [{
    lawId, title, previousHistoryId, currentHistoryId, revisedAt,
    status: "changed" | "unchanged" | "first_seen" | "unknown",
    errorCode?, sourceUrl
  }],
  nextSnapshot,
  coverage: { requested, checked, failed }
}
```

- 이름 검색의 모호성을 피하도록 첫 구현은 `LAW_ID` 목록을 받는다. 규정명은 기존 `search_rule` 또는 `lookup_dongguk_rule`에서 확인한다.
- 병렬 요청 수와 전체 실행 시간을 제한하고 한 규정의 실패를 다른 규정과 분리한다. 최신 연혁의 기존 캐시 정책과 확인 시각을 표시한다.
- `unchanged`는 확인된 최신 `HISTORY_ID`가 같다는 뜻이다. 원문 파일의 동일성, 시행일, 업무 적용성까지 같다는 판정이 아니다.
- 조회 실패는 `unknown`이다. 실패한 항목은 이전 스냅샷 값을 유지하고, 부분 응답을 새 전체 기준으로 덮어쓰지 않는다.
- 변경된 규정의 상세 내용은 `compare_rule_versions`로 후속 조회한다. 최초 조회에서는 변경이 있었다고 추정하지 않는다.

검증에는 일부 조회 실패, 잘못된 ID, 중복 ID, 최초 조회, 실제 버전 변경, 캐시된 최신 연혁을 포함한다. 날짜가 다르거나 단순 부분 일치한 후보를 곧바로 변경으로 세지 않는다. 참고 구현은 [korean-law-mcp의 search-bulk.ts](https://github.com/chrisryugj/korean-law-mcp/blob/main/src/tools/search-bulk.ts)이며, 이전 버전 맵·동시성 상한·개별 실패 분리 패턴을 사용한다.

정기 알림은 이 조회 도구와 별도 기능이다. 사용자 요청에 따른 예약, 변경 기준 저장 위치, 알림 대상이 결정된 뒤 검토한다.

## 2. 규정 간 인용·역인용 조회

**우선순위 높음 / 정방향 난도 중간, 역방향 난도 높음.** “이 조문이 참조하는 다른 규정”과 “이 조문을 인용한 규정”을 연결해 근거 누락과 개정 영향 확인을 돕는다.

제안 도구 계약:

```text
get_rule_references(
  law_id: integer,
  article: integer | string,
  history_id?: integer,
  direction?: "outgoing" | "incoming" | "both",
  limit?: integer
)

data: {
  source: { lawId, historyId, article, sourceUrl },
  references: [{
    direction, citationText, sourceLocation,
    scope: "same_rule" | "dongguk_rule" | "external_law" | "unresolved",
    target?, resolutionStatus
  }],
  coverage: { scope, indexedAt?, scannedRules?, totalRules?, complete },
  truncated, omittedCount
}
```

- 정방향은 지정한 개정본의 원문에서 명시적으로 인용한 규정·조문을 추출하는 작은 범위로 시작한다.
- 역방향은 전체 규정 본문 또는 명시한 규정 집합의 인덱스가 필요하다. 일부 규정만 조사했다면 `coverage.complete:false`로 표시하고 “전체에 인용 없음”으로 해석하지 않는다.
- “같은 조”, “전항”, 조문 범위, 부칙, 개정으로 이동한 조문, 생략된 규정명은 별도 해석이 필요하다. 확정할 수 없는 연결은 원문과 함께 `unresolved`로 남긴다.
- 역사적 규정의 인용을 현행 조문에 임의 연결하지 않는다. `history_id`를 지정한 조회는 원문의 시점과 대상 확인 시점을 따로 보존한다.
- 외부 법령의 명시적 인용과 법령의 적용 여부는 다르다. 자동 추출한 링크만으로 상위법 준수나 위임 적정성을 확정하지 않는다.

검증에는 같은 규정의 조문·다른 교내 규정·외부 법령·부칙·가지 조문·모호한 규정명·일부 인덱스를 포함한다. [KOICA 참조 구현](https://github.com/amnotyoung/koica-reg-mcp/blob/main/koica_search.py), [ALIO 외부 법령 연결 구현](https://github.com/scvcoder/korean-law-alio-mcp/blob/main/src/tools/alio/external-links.ts)을 참고했다.

### 후속: 하위규정 정비 후보 점검

**인용 관계 확보 후 / 구현 난도 중간 이상.** 모규정이 개정된 뒤 시행세칙·지침을 함께 검토할 후보를 찾는다.

```text
review_rule_dependencies(law_ids?: integer[], limit?: integer)

data.items: [{
  child, parent,
  relationEvidence: { kind: "explicit_citation" | "name_heuristic", location? },
  parentRevision, childRevision,
  status: "review_candidate" | "no_date_gap" | "unknown",
  changedReferencedArticles?
}]
```

이름 유사성은 관계 후보이고, 명시적 인용보다 약한 근거다. 모규정의 개정일이 더 최근여도 해당 하위규정에 영향을 주지 않았을 수 있다. 반대로 하위규정의 날짜가 더 최근이어도 필요한 내용이 반영됐다는 보장은 없다. 따라서 `no_date_gap`을 “정비 완료”나 “적법”으로 표시하지 않는다. 후속 단계에서는 변경된 모규정 조문과 하위규정의 인용 위치를 대조한다.

이는 [KOICA의 compliance_radar](https://github.com/amnotyoung/koica-reg-mcp/blob/main/koica_search.py)에서 착안한 제안이다. 날짜 비교만으로 내용 반영을 단정하는 문구는 채택하지 않는다.

## 3. 한국어 의미검색

**평가 자료 확보 후 / 구현·운영 난도 높음.** 규정 용어와 사용자의 일상 표현이 다른 질문에서 후보 조문을 넓힌다. 정확한 규정명·조문번호 조회와 원문 검증은 그대로 유지한다.

기존 `search_rule_deep`의 호환 옵션으로 확장하는 안:

```text
search_rule_deep(query, top?, per_doc?, mode?: "keyword" | "hybrid")

추가 결과 필드:
  searchMode: "keyword" | "hybrid" | "keyword_fallback"
  indexVersion?, indexedAt?, corpusCoverage?, fallbackReason?
  matchedBy, lawId, historyId, article, sourceUrl
```

- 실제 업무의 비식별 질문과 담당자가 확인한 규정·조문을 먼저 모아 평가셋을 만든다. 조문번호형·정식 규정명형·의역형·부정 질문·정답 없는 질문을 구분한다.
- 후보의 Recall@k뿐 아니라 엉뚱한 근거 상위 노출, 특정 조문 검색의 기존 정확도, 최초·반복 조회시간, 메모리 사용량을 함께 비교한다.
- 조문·별표 단위의 인덱스에는 `LAW_ID`와 `HISTORY_ID`를 포함하고, 결과 사용 전에 현재 원문과 연결한다. 과거 인덱스의 높은 유사도는 최신 근거가 아니다.
- 모델·인덱스를 읽지 못하면 기존 키워드 검색으로 전환하고 `keyword_fallback`을 공개한다. 규정명과 조문번호로 이미 정확히 지정한 조회는 의미검색에 의존하지 않는다.
- 로컬 모델을 선택해도 모델 다운로드·색인 재빌드·실행 메모리 비용은 발생한다. 임베딩 모델과 검색 점수만으로 법적 적용성이나 내용의 정답을 판정하지 않는다.

KOICA는 로컬 multilingual-E5와 키워드 검색을 결합하고 별도의 [한국어 의역 평가 스크립트](https://github.com/amnotyoung/koica-reg-mcp/blob/main/tests/evaluate_semantic_quality.py)를 둔다. 이 스크립트는 15문항의 Recall@10 및 키워드 대비 개선폭을 검사한다. 다른 기관의 작은 평가셋 결과는 동국에서의 효과를 입증하지 않으므로 자체 질문으로 재평가해야 한다.

| 현재 v1 계열 | `@modelcontextprotocol/sdk` 1.32.2 | 기존 import·서버 구조를 유지하는 호환 패치로 반영 |
| 공식 v2 계열 | `@modelcontextprotocol/server`, `client`, `core`, `server-legacy` 2.4.0 | 분리 패키지와 새 API로 전환하는 후속 마이그레이션 후보 |

공식 README는 v1을 `v1.x` 브랜치에서 유지하며 v2 출시일인 2026-07-27부터 최소 6개월간 버그·보안 수정 지원을 명시한다. 따라서 npm의 기존 `@modelcontextprotocol/sdk` 최신 버전과 저장소의 v2 최신 릴리스는 서로 다른 패키지 계열이다. [SDK 공식 README](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/README.md), [v2.4.0 릴리스](https://github.com/modelcontextprotocol/typescript-sdk/releases/tag/v2.4.0)

v2를 검토할 때는 import·transport·HTTP 수명주기·타입·오류·`structuredContent` 호환성, 기존 클라이언트 프로토콜을 함께 시험한다. 이번 의존성 수정에 v2 전환을 섞지 않는다. [공식 v2 전환 가이드](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2)

도구의 사람이 읽는 `title`은 [공식 Tool 명세](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)의 표시용 메타데이터이며, 이름·입력 계약을 바꾸지 않고 추가할 수 있다. korean-law-mcp 역시 v4.15.11에서 제목을 추가한 사례를 공개했다. [변경 기록](https://github.com/chrisryugj/korean-law-mcp/blob/main/README.md)

## 검증

- Node 24.22.1에서 전체 오프라인 30개 테스트 묶음 통과. 조문 문맥·번호 우선순위·제한 표시를 포함한 업무 조회 19개, 선택 범위·부칙 독립성을 포함한 원문 비교 19개, HWP 구조 23개 검사 포함.
- `npm audit --omit=dev`: 알려진 권고 0건. SDK 1.32.2와 `@hono/node-server` 2.1.6 외 패키지 버전 변경 없음.
- 캐시·로그인 쿠키를 끈 실제 MCP에서 여비규정 조회·최신 연혁·목차·존재하지 않는 개정본 거절·HWP 개정본 비교 등 9개 점검 통과.
- 학사·교원 인사·직원 근무·출장·회계·결재 권한·연구·학생 지원의 대표 규정 8건 모두 HWP 조회 성공. 검색 후보를 명시적으로 LAW_ID로 조회한 연결 검사이며 개별 업무 적용성 판단은 아니다.
- 새 설치본의 `finance` 프로필, 14개 도구의 한국어 제목, 취업규칙 제62조 발췌, 여비규정 제1조 선택 비교, 한국법령 공동 조회 경로를 확인했다.
- 국내 출장 공동 조회에서 법령 본문 2건을 확보했다. 종합 근거 상태는 `partial`일 수 있으며 이 검사는 지급 가능·비과세 적용의 최종 판정이 아니다.
- 독립 코드 검토에서 본칙 표 삭제가 부칙 표의 순번을 바꾸는 추가 결함을 재현하고, 본칙·개정일별 부칙의 구조 식별자를 분리했다.
- 패키지에는 소스·검사·문서·공개 예시만 포함한다. 로컬 설정·법령 인증정보·내부 자료팩은 포함하지 않는다.
